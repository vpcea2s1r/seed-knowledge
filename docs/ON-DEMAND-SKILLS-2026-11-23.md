# Обмен опытом между машинами: навыки по требованию (23.11.2026)

**Задача оператора:** на одном компьютере — веб-программирование и копирование сайтов (много правил/навыков), на домашнем — работа с текстами. Знания разрознены, домашнему приходится искать то, что знает «программирующий» комп. Как им обмениваться опытом?

## 1. Принцип

**Не копировать все скиллы на все машины.** Публикуем **карточку** навыка (имя, описание, теги, источник) в общий индекс, а **полный текст** `SKILL.md` держим в облачном хранилище и загружаем **только когда задача совпала**. Это тот же progressive disclosure, что в стандарте Agent Skills, но между машинами.

```
[Комп А: веб/копирование]  ──publish card + SKILL.md──┐
                                                     ├─► [Cloudflare: D1 индекс + KV тексты]
[Комп B: тексты]          ──skill_route("...")───────┘
                                    │
                                    ▼
                       skill_load(name) → полный текст в контекст этой задачи
                                    │
                                    ▼
                       feedback/observation с provenance → опыт доступен обоим
```

## 2. Роли

| Роль | Что делает |
|---|---|
| **Publisher** | Регистрирует карточку навыка (имя/описание/теги/машина) в D1 и кладёт `SKILL.md` в KV. Ничего больше не ставится |
| **Consumer** | Ищет по задаче (`skill_route`), получает список карточек, затем загружает нужный текст (`skill_load`) на время задачи |
| **Hub** | Cloudflare Worker + D1 (индекс) + KV (тексты) + Queues (запросы помощи). Центр управления |
| **Канон** | GitHub/SEED — версионируемая копия публичных скиллов; Hasleo/бэкап-сервер — приватные данные |

## 3. Что именно передаётся

- **Карточка** (всегда видна): `id`, `name`, `description`, `tags`, `machine`, `verified`, `updated`.
- **Тело навыка** (по запросу): `SKILL.md` — процедуры, правила, ловушки.
- **Опыт** (append-only): «урок → доказательство → проверка» с `provenance` (кто/когда/где замерено).
- **Приватный навык**: в индексе только описание + `visibility: private`; полный текст остаётся на своей машине, consumer шлёт `help-request` через Queue.

## 4. Почему это работает

1. **Контекст не раздувается**: загружается один релевантный навык, а не всё дерево.
2. **Актуальность**: обновил навык на komp A — оба видят новую версию сразу (в KV/D1).
3. **Подключение любой машины**: OpenCode на домашнем компе подключается к одному MCP URL и видит все навыки.
4. **Обратная связь**: домашний комп добавил observation — «программирующий» комп видит его при следующем поиске.

## 5. Секреты

В общий индекс **не попадают** пароли, внутренние IP, пути и приватные тексты. Санитайзер + `verified` + один писатель — как в SEED. Приватные данные — только бэкап-сервер, каталог 700.

## 6. Физически разные места (важно)

Прямого канала «комп A ↔ комп B» **не нужно**:

- оба компьютера обращаются к **одному глобальному Worker URL** по обычному HTTPS:443;
- исходящий трафик работает из-под домашнего роутера, NAT и офисного файрвола — **входящие порты не открываются**;
- Cloudflare — центр управления и единственная точка входа; D1/KV хранят индекс и тексты; GitHub — резервный канон;
- приватные навыки не покидают свою машину: в хабе только описание + `help-request` через очередь;
- токены доступа хранятся в OS-хранилище (Windows Credential Manager / Keychain), не в файлах;
- если Cloudflare недоступен, каждая машина работает из локального кэша последних загруженных навыков (offline fallback).

** Быстрый сценарий для двух машин:**

```
# на компе с веб/копированием (publisher)
seed skills-publish --name web-copy --file SKILL.md --tags web,copy --machine work

# на домашнем компе (consumer), из любой точки
seed skill-route "как копировать сайт"        # карточки + provenance
seed skill-load web-copy                      # полный текст в контекст текущей задачи
```

`SEED_HUB_URL` и `SEED_HUB_TOKEN` задаются в окружении; оба компа видят **один и тот же** индекс.

## 7. Эволюция концепции v2 (факты из интернета, 23.11)

Исследование дало **лучший стандарт**, чем наш придуманный REST:

- **MCP Skills Extension SEP-2640 (Final)** — официальное расширение MCP `io.modelcontextprotocol/skills`. Сервер объявляет capability, клиент вызывает `skills/list` (только name + description + frontmatter) и `skills/get` (URI + manifest), а файлы читает через `resources/read` **только по мере необходимости**. В манифесте — полный перечень файлов с **SHA-256** и размером; хост обязан верифицировать байты перед использованием.
- **Безопасность по стандарту:** контент навыка = **недоверенный ввод** (prompt-injection surface); origin сервера должен быть виден модели; **`resources/read` привязан к тому же серверу** (защита от confused-deputy); никакого неявного выполнения кода на хосте без отдельного одобрения; кэш на диске — immutable или с проверкой digest на каждом чтении; `Hosts MUST NOT retrieve files ahead of need`.
- **Port / virtual MCP** и **Skillmux** подтверждают ту же модель: один MCP URL на все машины, `list_skills` → `load_skill` → `publish_skill`; в Skillmux есть delivery tiers (Core pins, Routed — через MCP по требованию) и Git-backed vault как source of truth.
- **agentskills.io** фиксирует те же 3 стадии: Discovery → Activation → Execution.

**Вывод для нас:** не изобретать свои `skill_route/skill_load`, а **реализовать `io.modelcontextprotocol/skills` поверх нашего Worker**: D1 хранит карточки, KV — `SKILL.md` и ресурсы, манифест с SHA-256 выдаётся в `skills/list`, чтение — через `resources/read`. Это даёт совместимость с любым MCP-клиентом и встроенную проверку целостности. Наш REST остаётся как упрощённый fallback для скриптов.

## 8. Эволюция v3: машины, которых нет в базе (23.11)

Проблема оператора: **неизвестная машина не знает имени навыка** — она знает только задачу («мне нужно правило копирования сайта»). `/skills/<name>` тут не поможет.

**Факты из источников:**
- **ARD (Agentic Resource Discovery, v0.91)** — поле **`representativeQueries`**: 2–5 примеров естественно-языковых запросов, которые ресурс может обслужить; именно это поле отличает ARD-запись от простого каталога и по нему строится семантический индекс. Search API: `POST /search` с `query.text` (потребность) и `query.filter`; federation `auto|referrals|none`.
- **Google Cloud Agent Registry / AWS Agent Registry** — keyword search по метаданным и **semantic search по всему содержимому `SKILL.md`**; IAM-фильтрация результатов; MCP endpoint с инструментами search/list/get.
- **IETF DAWN «Survey of AI Agent Discovery»** — честно: **единого стандарта семантического discovery нет**; A2A/MCP/ANP описывают метаданные по-разному; MCP из коробки не умеет находить серверы (только предконфигурированные URL). Значит, нам нужен **свой слой discover**, совместимый со стандартами, а не надежда на «само найдётся».

**Решение v3 — три канала для неизвестной машины:**

1. **Карточка с representativeQueries.** Каждый навык публикуется не только с name/description, но и с 2–5 примерами запросов. Машина шлёт задачу текстом → хаб ищет по этим примерам + description + tags (пока JS-фильтр, потом embeddings).
2. **Need-очередь.** Если совпадений нет — создаём запись `need` (кто/что/когда) и через Queue рассылаем известным машинам; чья-то машина отвечает своим навыком, карта появляется в индексе с `verified=false` до одобрения.
3. **Федеративный поиск.** `federation: referrals` — хаб отдаёт ссылки на публичные реестры (MCP Registry, skills.sh, SkillsRegistry, ARD-совместимые), откуда можно подтянуть карточку внешнего навыка. Digests доказывают целостность, **не доверие** — контент остаётся недоверенным вводом.

**Self-registration:** неизвестная машина может сама опубликовать свой навык в своём namespace (`machine/name`), но он помечается `verified=false`, лимитируется по частоте и не получает права на выполнение кода без одобрения оператора.

## 9. Эволюция v4: подключение неизвестной машины или телефона

**Вопрос:** у устройства нет ни записи в базе, ни токена — как оно вообще попадает в систему?

**Модель zero-trust onboarding:**

| Шаг | Что происходит | Права по умолчанию |
|---|---|---|
| 1. **Invite** | Оператор создаёт одноразовый invite (имя устройства, срок, scopes) — в дашборде или через `POST /enroll` с admin-секретом | только на выдачу токена |
| 2. **Токен устройства** | Устройство обменивает invite на токен `se_…`; **plaintext показывается один раз**, в D1 хранится только SHA-256; токен кладётся в OS-хранилище (Credential Manager / Keychain), не в файлы | `discover`, `help`, `read` |
| 3. **Первый запрос** | Машина сразу видит каталог (`skills/list`) и ищет по задаче (`/discover`); телефон — через мобильный браузер/MCP-клиент с тем же URL | read-only |
| 4. **Self-registration** | Устройство может опубликовать свой навык в своём namespace `machine/name` | `publish`, но `verified=false`, лимит частоты, **без выполнения кода** |
| 5. **Повышение прав** | Оператор проверяет provenance и ставит `verified=true`; только после этого навык доступен другим как авторитетный | human-in-the-loop |

**Телефон:** специального приложения не требуется — достаточно браузера с HTTPS и (для POST) Turnstile; при необходимости тот же Worker отдаёт лёгкую HTML-форму `/phone`, а долгие задачи уходят в очередь `seed-help`. Нативный MCP-клиент на телефоне подключается к тому же URL.

**Жёсткие правила:** токен не в git/файлах/чате; admin-секрет — только в `wrangler secret` + OS-хранилище; все входящие тексты — недоверенный ввод; digest манифеста ≠ доверие; при утере токена — отзыв по `device_id`.

## 10. Реализация в хабе

- D1: таблица `skills` (карточки) + существующие `concepts/facts/experience/ideas/projects`.
- KV: ключи `skills/<machine>/<name>.md` с полным текстом.
- Worker: `skill_route(query)` → карточки; `skill_load(name)` → текст; `POST /skills/publish` → регистрация (writer-token).
- CLI на машине: `seed skills-publish`, `seed skill-route`, `seed skill-load` ( shipping в прототипе SEED).

Реализовано как продолжение `cloudflare/seed-edge`; см. `docs/TECHNICAL-SPEC-COMMON-SOURCE.md` §7 и `docs/MESH-INTEGRATION-RESEARCH-2026-11-22.md`.
