# ТЗ: система «Общий источник» (SEED — Shared Experience & Expertise Depository)

**Версия:** 0.9 (прототип → ТЗ, 22.11.2026)
**Статус:** проект решения, ожидает утверждения оператором
**Режим:** прототипирование в репозитории; прод-выкатка/публикация/сетевые записи — только по явной команде.

---

## 0. Почему это появилось (две боли оператора)

1. **«Новый комп = учить агента как ребёнка».** OpenCode ставится заново, но не знает правил проекта, инструментов, ошибок и решений.
2. **«Если комп сгорит или накроется диск — всё пропадёт».** Сейчас «мозг» агента (скиллы, память, граф) существует **только на этой машине**. Сервер выживает, мозг — нет.

Система должна решить **обе** боли одним механизмом: переносимый, проверяемый, избыточный источник, к которому агент подключается, а не который он заново изучает.

## 1. Назначение и границы

**Назначение:** хранить и выдавать версионируемый контекст, навыки и опыт так, чтобы:
- любой агент (OpenCode, Claude Code, Codex, Cursor) **запускался с готовым контекстом**;
- опыт из одной сессии становился **доступным другой машине/агенту**;
- гибель одного компьютера **не приводила к потере источника**.

**Не является:** агентом, моделью, вики, заменой репозитория кода, облачным сервисом с обязательным аккаунтом.

**Границы:** не хранит секреты в git/облаке/чате; не пишет в прод 1С; не меняет чужие файлы при установке пакетов.

## 2. Термины

| Термин | Значение |
|---|---|
| **Источник (source)** | Канонический набор файлов: правила, скиллы, факты, опыт, манифест. |
| **Пакет** | Папка с манифестом + текстом/инструментами; координата `group/name`, версия. |
| **Манифест** | `manifest.json`: версия, перечень файлов, SHA256, дата, флаг санитизации. |
| **Lockfile** | Точный список установленных версий/хэшей — воспроизводимость. |
| **Boot lane** | Упорядоченный список чтения; агент читает его в начале сессии. |
| **Опыт (experience)** | Запись «трассировка → знание» по схеме T2K (FailurePattern/FixPattern/Procedure/Heuristic). |
| **Bootstrap** | Подключение новой машины к источнику: установка + верификация + сид памяти. |

## 5. Архитектура (три плоскости)

```
                  [ ПЛОСКОСТЬ ИСТОЧНИКА ]
   GitHub repo (канон; read-only для агентов)
   ├── source/manifest.json  (SHA256, версия)
   ├── source/boot-lane.json (порядок чтения)
   ├── source/SKILL.md       (точка входа для любой модели)
   ├── source/rules/         (AGENTS.md, санитизированный)
   ├── source/skills/        (навыки)
   ├── source/knowledge/facts.json
   └── source/experience/records.jsonl (append-only, T2K)
            │ git clone / raw / CDN / MCP
            ▼
   [ ПЛОСКОСТЬ ДОСТАВКИ ]  Cloudflare Worker + R2 (P1)
   - R2: 10 ГБ бесплатно, egress free (docs 22.11.2026)
   - Worker: 100k req/day free; MCP-over-HTTP
            │
            ▼
   [ ПЛОСКОСТЬ ВЫЖИВАНИЯ ]
   1) GitHub (вне этого компа)         — канон, версии
   2) Бэкап-сервер 10 ТБ (вне этого компа) — приватный архив, метка 700 + публичный архив
   3) knowledge-web :8090              — read-only зеркало (сейчас LAN)
   4) Локальная копия на этом компе    — fastest restore, НЕ считается резервной
```

**Правило 3-2-1:** ≥3 копии, ≥2 разных носителя/провайдера, ≥1 вне этой машины. Сейчас выполнено 2 из 3 (сервер + локально) — не хватает **автоматической синхронизации «мозга»** на сервер.

## 6. Модель данных

### 6.1 manifest.json (генерируется `seed build`)
```json
{
  "schema": "seed.manifest/1",
  "version": "0.1.0",
  "generated_at": "2026-11-22T...",
  "sanitized": true,
  "files": [{"path":"skills/x/SKILL.md","sha256":"...","bytes":1234}],
  "counts": {"files": 12, "bytes": 45678}
}
```

### 6.2 boot-lane.json
```json
{"schema":"seed.boot-lane/1","read":[
 "rules/AGENTS.md",
 "SKILL.md",
 "knowledge/facts.json",
 "skills/1c-config-version/SKILL.md"
]}
```

### 6.3 facts.json — факт с provenance
```json
{"id":"F-001","claim":"Версия конфигурации 1С — только из Configuration.xml",
 "source":"XML-выгрузка fresh-base, замер 22.11.2026","verified":true,
 "confidence":1.0,"created":"2026-11-22"}
```

### 6.4 experience/records.jsonl — T2K-запись
Поля: `id`, `kind` (`FailurePattern|FixPattern|Procedure|Heuristic`), `claim`,
`evidence`, `confidence` (0–1), `verified`, `created`, `supersedes`, `applies_to`.
Замеренные утверждения помечаются `verified: true`; непроверенные — `false` (не смешивать).

## 7. Интерфейсы

### 7.1 CLI `seed <command>` (прототип, stdlib)
`build | verify | install --target <dir> | search <query> | feedback --kind ... --claim ... --evidence ... | status`

### 7.2 Boot block в AGENTS.md (пишется install'ом, идемпотентно)
```

Источник: <путь>/boot-lane.json. Прочитай файлы по порядку перед работой.

```

`source_search`, `source_get`, `experience_append` (только writer), `source_verify`.

### 7.4 HTTP (P1)
`GET /manifest.json`, `GET /files/<path>`, `GET /health`, `POST /feedback` (writer-token).

## 7.5 Ежедневный контур развития и федерация проектов

### 7.5.1 Ежедневный контур (SEARCH → ANALYZE → DECIDE → RECORD → VERIFY)
Не изобретаем заново: опираемся на `docs/SELF-LEARNING.md`, `docs/AUDIT-PROTOCOL.md` (AU-1), `docs/LESSONS-INBOX.md`, скилл `session-retro`. Что добавляет SEED — **ежедневный триггер и измеримые метрики поиска/анализа**:

| Шаг | Действие | Артефакт |
|---|---|---|
| SEARCH | 1–3 вопроса дня; поиск по памяти, файлам, внешним источникам (по команде) | `daily/YYYY-MM-DD.md`, раздел «поиск» |
| ANALYZE | отделить факт от гипотезы; источник + дата замера; что у соседей | `facts.json`, `daily/metrics.jsonl` |
| DECIDE | одно улучшение: новый факт/скилл/правка поискового паттерна | `experience/records.jsonl` (kind=Heuristic/FixPattern) |
| RECORD | mcp-memory (observations), Semantica (`record_decision`), ORCHESTRATION-LOG | запись с датой |
| VERIFY | на следующий день: сработало ли (hit-rate, время, повтор ошибки) | метрика в `daily/metrics.jsonl` |

**Метрики (обязательно числом):**
- `search_hits` — доля вопросов дня с найденным подтверждённым ответом;
- `time_to_answer` — время до первого проверенного факта;
- `repeat_errors` — число повторных ошибок (цель 0);
- `verified_ratio` — доля фактов с `verified: true`;
- `neighbor_findings` — сколько идей/навыков найдено у других проектов.

Правило: «стало лучше на глаз» не принимается; тихий проход валидатора = провал (AGENTS.md).

### 7.5.2 Федерация проектов
**Факт (замер 22.11):** в `C:\project` — 21 каталог; `.opencode/skills` есть только у `1с` (54) и `site_ngl` (57); AGENTS.md — у `1с`, `site_ngl`, `abitur.lunn.ru`, `proxy_gost`. В agentmemory 24 сессии: `1с` 10 (3297 obs), `site_ngl` 11 (4131), `free_api` 1 (212), `pfxd` 2 (595).

**Модель:** у каждого проекта свой namespace `project/<name>/...`; общий слой — только санитизированные индексы:
```
source/projects/registry.json   # проекты, кол-во скиллов/фактов/сессий, дата замера
source/projects/<name>/index.json # что проект может предложить (идеи, скиллы, опыт)
source/ideas/catalog.jsonl        # идеи с статусом open/adopted/rejected + provenance
```
**Правила:** read-all / write-own (один писатель на проект); секреты проекта остаются в его приватном архиве; кросс-проектный поиск идёт по индексам, а не по сырым БД.

**Почему не `agentmemory mesh_sync`:** по факту 21.11 — требует `AGENTMEMORY_SECRET` и второго пира; на бэкап-сервере agentmemory не запущен, секрет в файлы писать запрещено. Рабочая замена — общий файловый/гит-источник + `knowledge-web` :8090.

## 7.6 Как машина просит помощи (HITL-канал)

Машина не может позвонить агенту напрямую; она **пишет запрос в общий канал**:

| Канал | Статус | Как работает |
|---|---|---|
| `seed help-request --from <machine> --question ...` в `source/requests/inbox.jsonl` | **работает сейчас** (P0) | append-only JSONL; агент читает `help-inbox`, отвечает `help-resolve`; у запроса есть id, отправитель, срочность, статус |
| `memory_signal_send / memory_signal_read` (agentmemory) | инфраструктура есть, mesh не работает без `AGENTMEMORY_SECRET` и второго пира | сигнал `info|request|alert|handoff` между агентами |
| Cloudflare Worker `POST /help` + R2/D1 | P1, по команде оператора | внешний HTTP-канал, доступен из любой точки интернета |
| Telegram/почта-бот | P2, по команде | токены/секреты — только на бэкап-сервере |

Правило: запрос помощи **не даёт права трогать прод**; решение остаётся у оператора. Ответ фиксируется в журнале с id и датой (audit trail).

## 7.7 Уроки из Claude Code Ultimate Guide (факты 22.11, идеи не текст)

Источник: `FlorianBruniaux/claude-code-ultimate-guide` — 6817★, 859 forks, создан 09.01.2026, push 22.11.2026, v3.46.0, лицензия **CC-BY-SA-4.0** (поэтому забираем только паттерны и пишем своими словами, не копируем текст).

1. **Шесть стадий памяти:** `captured → stored → indexed → retrievable → injected → effective`. Каждая стрелка может сломаться молча. Наш smoke проверяет первые пять (запись, манифест, search, boot block); sixth («агент реально применил») измеряем метрикой `repeat_errors` в ежедневном контуре. Лечится не «есть строка в БД», а проверкой каждой стадии.
2. **Память — координаты, а не стопка слоёв:** оси `content` (факт/процедура/эпизод), `form` (файл/БД/граф/токены), `scope` (сессия/машина/проект/команда/флит), `lifecycle` (write→retrieve→consolidate→supersede→forget). Наш T2K-журнал уже имеет `supersedes`; добавляем `scope` в схему записи (P1).
3. **Отражение атаки:** общая память — **незащищённая поверхность записи**. Любой участник или скомпрометированная зависимость может внедрить инструкцию, которую прочитают все будущие сессии. Наши меры: один писатель, санитайзер, provenance, `verified` и запрет автоматического исполнения build-шагов внешнего пакета.
4. **Hook-driven capture > MCP-driven:** автоматический захват хуками дешевле (0 токенов) чем ручной вызов записи (20–50 токенов). Сейчас наш `feedback` — ручной; автоматический захват — P1.
5. **Гибридный поиск:** BM25 + вектор + граф (RRF) даёт +9 п.п. R@5 против чистого вектора. У нас уже есть граф (Semantica) и полнотекстовый поиск — кандидат на fuse (N10).
6. **Машиночитаемая навигация:** `machine-readable/navigation.json` с `$schema`, `groups[]`, `items[]` (`source_path` + `site_path`) — один контракт для README и сайта. Берём структуру (свои описания) в `source/navigation.json`: так `knowledge-web` и канон не расходятся.
7. **Три трека памяти:** нативный/кросс-сессионный/командный; командный трек структурно не заполнен рынком. Наш SEED — попытка закрыть именно его через общий файловый источник + федерацию проектов.

## 8. Безопасность

1. **Санитайзер до публикации:** регулярки на пароли/токены/внутренние IP/персональные логины/пути `[local-path]`, `[user-path] любая находка → `sanitized: false` и блок публикации.
2. **Два дерева:** пользовательские правила и копии пакетов разделены; установка пишет только в копии.
3. **Секреты:** приватный архив (содержит `memory.db` с паролями) — **только** бэкап-сервер, каталог с режимом 700; в git/облако/чат не попадает никогда.
4. **Single writer:** append-only журнал опыта; запись только через `feedback` с аудитом.
5. **Human-in-the-loop:** повышение `verified` для непроверенного опыта — только по команде оператора.
6. **Лицензии:** каждый файл/source имеет лицензию; заимствованные скиллы — только совместимые.

| B2 — NAS/второй диск | `[local-path]`, `[local-path]` | dt, патчи, архивы | есть, но тот же офис/сеть: уязвима к пожару и шифровальщику |

| B4 — GitHub origin | `github.com/vpcea2s1r/1c-dokumentturnover` | санитизированный канон | **есть, но последний push 15.11** — всё новое отсутствует |

**Требование:** ≥3 активные корзины, ≥2 разных провайдера, ≥1 вне этой машины, ≥1 офлайн/неизменяемая. У каждой корзины — контрольная сумма, дата и дрилл. «Корзина» не считается активной без факта записи и проверки (один только remote в git — не бэкап).

### 9.3 Процедуры
- **dr-pack (P0):** сборка архивов + `SHA256SUMS` + отчёт санитайзера; артефакты в локальном temp, дальнейшая отправка на сервер — только по команде.
- **Синхронизация (P1):** по расписанию (GitHub Actions + scp на бэкап-сервер), с проверкой контрольных сумм.
- **Дрилл (P1, ежеквартально):** восстановление на чистую папку из **удалённой** копии, сверка SHA256, запуск smoke-теста. «Бэкап без дрилла не считается бэкапом» (урок 22.11).
- **История:** версионируемые снимки (дата + хэш), не «latest» перезаписью; `latest` — относительный симлинк (урок nginx :8090).

### 9.4 Runbook «комп сгорел»
1. Новый комп: установить OpenCode + Python 3 (по `docs/ONBOARDING`).
2. Получить публичный архив из GitHub/../../R2; приватный — с бэкап-сервера (доступ по ключу, каталог 700).
3. `seed install --target <project>` → проверка `seed verify`.
4. Восстановить `memory.db` из приватного архива в `%USERPROFILE%\.config\opencode\mcp-memory\` (только на новой машине).
5. Проверить: скиллы N, факты N, MCP health, `search` по контрольному запросу.
6. Записать в `ORCHESTRATION-LOG`: дата, хэш архива, результат.

## 11. Критерии приёмки (измеримые)

1. `python tools/seed.py build` → `manifest.json` с корректными SHA256; `verify` → OK.
2. `seed install --target <temp>` → в целевом каталоге boot block, lockfile, все файлы; пользовательский `AGENTS.md` не изменён вне маркеров.
3. `search "ibcmd"` находит хотя бы 1 факт/запись опыта.
4. Санитайзер: тестовый секрет в файле → `sanitized: false`, публичный архив **не** содержит строку секрета.
5. `dr-pack` создаёт приватный и публичный архивы + `SHA256SUMS`; приватный не попадает в git.
6. Время установки на «чистую машину» (temp-каталог) ≤ 5 мин.
7. Смoke-тест после «гибели компа»: восстановление из архива в temp → `verify` OK → `search` находит контрольный факт.
8. `projects` показывает ≥2 проекта с измеренными счётчиками; `mesh-search "навык"` находит запись из чужого namespace.
9. `daily` создаёт запись с 5 полями (SEARCH/ANALYZE/DECIDE/RECORD/VERIFY); `daily-report` считает метрики за 7 дней.
10. `distribute` формирует план из ≥3 корзин с командами проверки SHA256; ни одна корзина не помечается выполненной без замера.
11. `bootstrap` на чистой папке за ≤5 мин устанавливает источник и (при наличии приватного архива) восстанавливает память с SHA256-проверкой; отчёт `bootstrap-report.json` содержит время.
12. `help-request` → `help-inbox` → `help-resolve` закрывает цикл «машина попросила помощи» с id и датой.
13. `navigation.json` описывает ≥4 intent-группы; каждый локальный `source_path` существует в источнике.

## 12. Риски и меры

| Риск | Мера |
|---|---|
| Секрет попадёт в git/облако | санитайзер + приватный архив только на сервере 700; `.gitignore` |
| Архив «latest» перезапишется битым | версионированные снимки + SHA256 + дрилл |
| Зависимость от одного автора/вендора | канон в git (можно форкнуть), формат — простой JSON, без проприетарного движка |
| Опыт окажется непроверенным | `verified` флаг, provenance, human-in-the-loop |
| Рост контекста | boot lane короткий, длинное — по ссылке |

## Приложение А — решение об «улучшении идей»

Идеи оператора усилены четырьмя проверенными паттернами (факты из этой сессии):
- **VibeVM** (`vibevm.org`, 68★, Rust, push 22.11): `vibe.toml` + lockfile + boot lane + two-tree rule + агент-независимость. Берём формат, **не зависимость** (проект молодой, один автор).
- **T2K** (`vibe-machine/ontology-trace-to-knowledge`): онтология «трасса → знание» для журнала опыта (`docs/ONTOLOGY-T2K-REFERENCE.tql` уже есть).
- **Vibe Machine** (iPhone-кокпит): конвейер стадий и «чеки» (токены/время) как источник телеметрии; QR/pinning/Allow-Deny как модель HITL.
- **1С-практика этой сессии**: `Configuration.xml` — единственный авторитет версии; пустой лог ≠ успех; обёртки с WaitForExit убиваются → detached + монитор; кириллица в путях искажается → ASCII.
